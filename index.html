PERFORMANCE

Performance: Isolated

Dolby Vision test method

Dolby Vision carries dynamic metadata that changes from scene to scene, and a tone mapper has to follow those changes. A loop of one repeated frame keeps the metadata constant and leaves that work out. From our observations, the metadata changes in a way that matters for tone mapping on roughly 3 to 8% of the frames of typical content, around 5% in the middle, which is about once every 20 frames. Some content barely changes at all.

The test therefore takes eight frames from different scenes of the source and repeats each of them 20 times. The resulting 160-frame sequence loops with a metadata change every 20 frames. GPU frames are uploaded once before the loop and stay on the GPU. The sampling position, stride and frame counts are fixed in the workload configuration and are the same on every machine.

Each sample pairs the configured short and long runs, both containing whole 160-frame passes. Per-frame cost is (long time − short time) / (long frames − short frames), and the result is the median of three valid pairs. The configured method stays fixed; a single-frame case is labelled accordingly.

Isolated test method

The isolated test measures the tone mapper on its own, without decoding and encoding. Each run decodes the first frame of the original clip, applies any input conversion the filter requires once, and uploads GPU frames once. It then repeats that one prepared frame N times through the tone mapper. The output goes to the null muxer as wrapped frames: GPU frames stay on the GPU, and nothing is downloaded or encoded.

Each sample pairs a run with one frame and a run with N frames. Per-frame cost is (time(N) - time(1)) / (N - 1); FPS is its inverse. The subtraction removes startup, decoding, upload and any one-time setup of the tone mapper. Duration is the wall time of the N-frame run, including those startup costs.

N is fixed for each case in config/performance-workloads.json. Every machine processes the same workload; previous results, calibration runs and measured speed do not change N. Clearing results leaves the workload configuration intact. Explicit frame-count overrides are recorded as custom comparisons.

The result is the best valid sample. Spread is (max FPS - min FPS) / max FPS across the valid samples. A repeated frame keeps its HDR metadata constant, so this test does not include the work of following changing dynamic metadata; Dolby Vision uses its eight-state method for that. Output conversions that a filter needs remain in the measured chain, for example the zscale steps around stock tonemap.

Full transcode test method

The full transcode test uses the fixed output frame count or media duration recorded for each case: decoding, tone mapping at native resolution, scaling to 720p and H.264 encoding. GPU routes keep frames on the GPU from decoder to encoder, without any upload or download: CUDA with NVENC, OpenCL with QSV on Intel or with AMF on AMD, and Vulkan with Vulkan Video. On AMD, Emby maps between AMF and OpenCL and scales with vpp_amf, like the Emby server; the other builds map between D3D11 and OpenCL and scale with scale_d3d11. Software filters decode in software and encode with libx264 ultrafast.

With one tone mapping pass per frame, fast GPU tone mappers are hidden behind the hardware decoder, and all of them end up at the decoder's limit. GPU routes therefore pass every decoded frame through tone mapping five times. fps=source_fps*5 repeats each frame before it is mapped into the tone mapper's API, and fps=source_fps/5 keeps one of the five after it is mapped back, right before the scaler. Mapping in, tone mapping and mapping back run five times per output frame; decoding, scaling and encoding run once. Software routes use a single pass.

FPS is output frames divided by FFmpeg's wall time. Mapped FPS counts the tone mapping passes: five times FPS on GPU routes, equal to FPS for software. Speed is output frames divided by the source frame rate and the wall time. Duration is the wall time of the run, and the result is the best valid sample.

Very fast tone mappers can still reach the limit of the decoder or encoder; their FPS is then a lower bound. Routes that a build cannot run, for example because its D3D11-to-OpenCL mapping is missing, are listed as failed or skipped with the native error rather than replaced by a software path.
